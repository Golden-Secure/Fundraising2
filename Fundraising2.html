01 Introduction & Scope

1.1 Purpose

This document specifies the engineering implementation of Fundraising Events Completion v2.0. It is a pure technical specification — no design or wireframe content. All references to feature names, error codes, and schema follow the patterns established in v1.1.

1.2 In Scope (v2.0 additions)

  • Recurring event donations (monthly / yearly / custom)
  • Per-user ticket limits (free & paid)
  • Stripe refunds (tickets + donations)
  • Promo & discount codes
  • Offline / manual donations & manual ticket issuance
  • Donation records table (unified ledger view)
  • Event summary KPIs + donations dashboard
  • Bundle inventory deduction & proportional availability constraint
  • Hold-race notifications + sold-out waitlist
  • Push reminders + custom FCM icon
  • Add-to-calendar (ICS generation)
  • Data export (CSV / XLSX)
  • QR scanner (admin web + mobile admin mode)
  • Pledged vs. Collected donations tracking
  • My Tickets redesign fields
  • Small fixes batch (Arabic title, tier name, date+time merge, etc.)

1.3 Out of Scope (v2.0)

  • Live Auction & Bidding — marked for v3.0 module
  • External dedicated QR scanner app — deferred to v3.0
  • E-transfer donor flow
  • Alternate payment gateways
  • Web SCA redirect completion — accepted v1 gap

2.3 Idempotency Model

  • Ticket issuance: unique composite (source_reference, seq_no) on fundraising_tickets.
  • Donation listener: WithoutOverlapping('fundraising-event:{id}') + row lock on the event.
  • Promo code usage: atomic increment('used_count') inside a DB transaction.
  • Refund: unique stripe_refund_id in fundraising_refunds.

{
  "reason": "User requested refund",
  "amount": "100.00",          // optional; defaults to full
  "send_notification": true

Backend flow:

  1. Validate ticket not already refunded → else EVENT_REFUND_ALREADY_PROCESSED.
  2. Call Stripe Refund API against original PaymentIntent.
  3. Persist row in fundraising_refunds with status pending.
  4. On webhook charge.refunded: set status completed, dispatch EventTicketsRefunded.

Only for source=online. Offline donations cannot be refunded via Stripe.

08 Background Jobs & Scheduled Tasks

JobSchedulePurpose
ProcessRecurringDonationsJob Daily 02:00 Charge due schedules via Stripe. On success: dispatch EventDonationCompleted(source=recurring). On failure: increment failure_count; auto-cancel after 3.
ScheduleEventRemindersJob Hourly Find events starting within the next 1h (configurable), send event_reminder FCM to all ticket holders.

8.1 Job Skeleton — ProcessRecurringDonationsJob

class ProcessRecurringDonationsJob implements ShouldQueue
{
    use Dispatchable, InteractsWithQueue, Queueable;

    public function handle(StripeClient $stripe): void
    {
        RecurringDonationSchedule::query()
            ->where('status', 'active')
            ->where('next_charge_date', '<=', now())
            ->chunkById(50, function ($schedules) use ($stripe) {
                foreach ($schedules as $schedule) {
                    try {
                        $charge = $stripe->paymentIntents->create([
                            'amount'         => (int) ($schedule->amount * 100),
                            'currency'       => strtolower($schedule->currency_code),
                            'customer'       => $schedule->stripe_customer_id,
                            'payment_method' => $schedule->stripe_payment_method_id,
                            'confirm'        => true,
                            'off_session'    => true,
                        ]);

                        EventDonationCompleted::dispatch(
                            tenantId:          tenant('id'),
                            eventId:           $schedule->event_id,
                            amount:            $schedule->amount,
                            currencyCode:      $schedule->currency_code,
                            reference:         $charge->id,
                            source:            'recurring',
                            userId:            $schedule->user_id,
                            isZakat:           $schedule->is_zakat,
                            recurringScheduleId: $schedule->id,
                        );

                        $schedule->update([
                            'next_charge_date' => $this->nextDate($schedule),
                            'failure_count'    => 0,
                        ]);
                    } catch (\Throwable $e) {
                        $this->handleFailure($schedule, $e);
                    }
                }
            });
    }
}

10 Feature-by-Feature Implementation Guide

10.1 Recurring Donations

Backend:

  1. Migration: recurring_donation_schedules (§4.1).

10.3 Refund System

See §6.2. Listener sketch:

class TicketsRefundedListener
{
    public function handle(EventTicketsRefunded $event): void
    {
        DB::transaction(function () use ($event) {
            $ticketType = TicketType::lockForUpdate()->find($event->ticketTypeId);
            $ticketType->decrement('tickets_sold_count', $event->quantity);

            FundraisingTicket::whereIn('code', $event->ticketCodes)
                ->update(['status' => 'refunded', 'refunded_at' => now()]);

            FundraisingEvent::lockForUpdate()->find($event->eventId)
                ->decrement('raised_amount', $event->amount);
        });

        broadcast(new FundraisingEventProgressUpdated($event->eventId, 'refund'))->toOthers();
    }
}

10.7 Bundle Inventory Deduction

Schema: is_bundle, bundle_size, bundle_parent_ticket_type_id on fundraising_ticket_types.

On reservation of a bundle:

$parentType = TicketType::lockForUpdate()->find($bundle->bundle_parent_ticket_type_id);

    throw new TicketCapacityExceededException($parentType->id, 0);

$parentType->increment('tickets_sold_count', $deduction);

10.8 Proportional Availability Constraint

$available = $parentType->capacity - $parentType->tickets_sold_count - $activeHolds;

14 Testing Strategy

14.1 Backend (Pest)

  • Feature tests: every endpoint — happy path + each registry error.
  • Concurrency: two parallel reserve() calls for the last seat — one succeeds, one receives EVENT_TICKET_CAPACITY_EXCEEDED.
  • Idempotency: replay the same webhook twice — no double ticket issuance; no double raised_amount increment.
  • Reconciliation: seed drift → run job → assert corrected.
  • Recurring: simulate Stripe charge success and failure; verify next_charge_date rollover, failure_count handling, auto-cancel after 3.
  • Refund: full refund, partial refund, refund of already-refunded ticket → EVENT_REFUND_ALREADY_PROCESSED.
  • Promo codes: expired, usage-limit reached, wrong ticket type, concurrent redemption atomicity.
  • Bundle: bundle purchase deducts correct quantity; proportional constraint returns Sold Out.
  • User limits: concurrent purchase of the last allowed ticket → only one passes.

14.2 Frontend (Jest + RTL)

  • Payload builders (toEventDonationCartItem, toDirectTicketCheckout) snapshot tests.
  • Error code branches (422 codes + 409 mismatch).
  • Recurring toggle state → payload shape.
  • Poll-timeout behavior on /tickets?payment_flow_id=.

14.3 Mobile (Flutter Test)

  • Model fromJson round-trips against v2.0 fixtures.
  • Bloc tests: EventCheckoutBloc failure branches for every code.
  • FCM navigation switch — including unknown type default.
  • Topic subscribe/unsubscribe lifecycle.
  • Cart ID regression (top-level only).

14.4 End-to-End (M3)

  • Guest → login → recurring donation → progress bar updates on web + mobile.
  • Two concurrent buyers on last ticket: one succeeds, one receives EVENT_TICKET_CAPACITY_EXCEEDED + hold-release FCM.
  • Bundle purchase reduces individual capacity correctly.
  • Refund frees a seat → waitlist user gets ticket_availability push.

  • Data export downloads correct number of rows for tickets & donations.

Deploy ordering MediumHigh Deploy enums + migrations atomically; Horizon restart

18 Appendix B — Glossary

TermDefinition
Direct CheckoutThe one-tap purchase path via Billing module — no cart involvement.
HoldA row-locked reservation of ticket quantity with a 30-minute TTL, taken at payment/start.
Soft CheckA non-committing availability verification at create/flow.
CommitThe single-writer step in the listener that consumes the hold and creates tickets.
BundleA ticket type that deducts N individual tickets from the parent type when purchased.
Proportional ConstraintThe rule that a bundle is available only if parent.remaining >= bundle.size.
PledgedA committed donation that has not yet been collected (deferred, check, recurring commitment).
Opt-In (Waitlist)A user's request to be notified when a sold-out ticket becomes available.
Hold RaceConcurrent payment where one user's hold is displaced by another's completed purchase.
Idempotency Keysource_reference + seq_no on ticket rows; prevents duplicate issuance on webhook replay.
