Event Day Load Test

Results of the Smoke, Load and Stress runs from the October load test plan, the breaking point of the current setup, why it breaks, and what to change before the event day.

Not ready for the event day

  • The server holds about 20 requests per second with acceptable speed. The plan's Load run needs about 150 requests per second; the event day (10,000 visitors, thousands with the page open) needs several hundred.
  • At the expected load, 99.9% of requests failed (HTTP 503 and 20–30 s timeouts) from the first minute to the last.
  • Buyers got errors for purchases that succeeded: 9 free tickets were issued while the buyer received only errors. On the real day a buyer would retry and buy twice.
  • No 429s: the rate limits were not the problem. The failures come from the hosting layer running out of capacity, and the application is slow even with no load (300–500 ms for the progress bar).

Purchases succeeded while the buyer saw an error. The buyer account holds 10 tickets for the event: 1 from Smoke (09:27 UTC) and 9 issued between 09:33 and 09:37 UTC, during the Load run, when every purchase response k6 received was a 5xx or a timeout. The buyer was then refused with "You have reached the maximum of 10 free tickets for this event".

On the real day this means: a buyer sees an error, tries again, and gets (or pays for) a second ticket. For paid tickets this is the "charged exactly once" risk in section 8 of the plan.

After the run: the first request at 09:49 UTC waited 85 s and got a 504; the next ones answered normally in about 0.7 s. The environment recovered by itself within a couple of minutes.

3. Stress · where it breaks

Breaks at 20–35% of Load

The plan's Stress run starts at 600 visitors/min, which already failed completely in the Load run, so it could not show where the server breaks. It was run as a stepped test instead: the Load mix (600 new visitors/min + 1,000 staying) at 10, 20, 35, 50, 75 and 100%, 3 minutes per step, stopping on its own once a step passed 30% errors.

What breaks first, in order:

  1. Response time (step 2): every request still succeeds, but waits 12–15 s in a queue. The server is saturated at roughly 25–35 requests per second.
  2. Fast rejections (step 3): HTTP 503 in about 190 ms, text/plain, from the platform layer (Cloudflare / Laravel Cloud). These responses carry no X-RateLimit header, so the application never saw them: no worker was free to take the request.

Responses by code in this run: 8,085 × 200, 46 × 503, 22 × 422 (the buyer's 10-ticket limit, see above). The progress bar already missed its 0.8 s target at step 1.

4. Spike and Soak

Not run

The Spike run (5,000 visitors/min, about 750 requests per second) and the Soak run assume the Load run passes. With a breaking point near 30 requests per second they would only repeat the Load result and keep the shared test environment down longer. Run them after the changes below.

Why

Why each request is so expensive

From reading the backend code (the hosting settings themselves are not in the repository, so some points need confirming in Laravel Cloud). Every public request does a lot of database work that never changes between visitors.

A page load of the event (9 calls) therefore costs well over 60 database queries, and each open page adds about 12 more every 10 seconds. At 3,000 open pages that is 300 progress calls per second, about 10 times what the server holds today.

Recommendations

What to change before the event day

Ordered by impact. Scaling the servers alone will not close a 10–20× gap affordably: the biggest gain is to stop recomputing the same answers for every visitor.

Priority 1Server

Give the API more room and fail fast

  • In Laravel Cloud: raise the app compute size and the number of instances, and set autoscaling with a minimum of several instances warm before the event starts (autoscaling reacts in minutes; the spike comes in one).
  • Confirm Octane is on, and size its workers to the instance's CPU.
  • Point DB_HOST at the database's connection pooler (the -pooler endpoint) so hundreds of workers do not open hundreds of Postgres connections each second; scale the database up for the day.
  • Use Redis (Valkey) for the cache and the rate limiter, never the database store.
  • Add connect and statement timeouts (for example 5 s) so a slow query fails fast instead of holding a worker for 20–30 s.
  • Run the event on its own database, not on npos_shared with other environments.
Priority 1Application

Cache what every visitor sees

  • Layout calls (branding, tenant info, languages, header, footer, social, contact): cache per tenant for 5–10 minutes and clear on save. They change a few times a month and are 7 of the 9 calls of every page load.
  • Progress bar: cache the snapshot per event for 5–10 seconds. Better: send Cache-Control: public, s-maxage=5 so Cloudflare answers it, with the tenant in the cache key (path or host instead of the X-Tenant header). This turns thousands of requests per minute into a few.
  • Event page: cache the published event per slug for 30–60 seconds; keep ticket availability live.
  • Middleware: turn on tenant resolver caching (stancl CachedTenantResolver), cache the active-subscription and plan checks per tenant for a minute, and use the cached default language.
  • Fix the header/footer N+1 (eager-load the translations); add the missing tenant_id indexes on central.subscriptions and central.domains.
Priority 1Purchases

Never let a buyer buy twice after an error

  • Accept an Idempotency-Key on POST /client/tickets/intent (the offline donation endpoint already has this mechanism) so a retry returns the first purchase instead of creating a second.
  • On the site: after a timeout or 5xx on purchase, check "my tickets" / the intent status before showing an error or allowing a retry; show "We are confirming your order" instead of a failure.
Priority 2Verify

Check whose IP the rate limits count

Reading the code, the throttles appear to run before the app's TrustProxies middleware (Laravel sorts throttles above most middleware). If so, the per-IP limits may count Cloudflare's or the BFF's address instead of the visitor's, and on the event day thousands of real visitors would share one 1,000/min limit. Confirm with gatherRouteMiddleware on a public route; if confirmed, move proxy trust to the global middleware.

Priority 2Site

Poll less

The backend already publishes progress updates (EventProgressPublisher). If the event page listens to them, the 10-second polling can become a 30–60 second fallback, which alone cuts the progress traffic by 3–6×.

Priority 3Next test

Test again after the changes

  • Run the stepped breaking-point test first (about 20 minutes); move to Load only once 100% of the Load mix passes, then Stress and Spike.
  • Provide tokens.txt with the 300 buyers, and raise EVENT_TICKET_MAX_FREE_PER_USER_PER_EVENT (default 10 free tickets per buyer per event) for the test: this run had one buyer, capped at 8 purchases per minute.
  • Above about 1,000 requests per minute, the per-IP limits apply to the test machine: raise them for the test, or run from several machines.
  • The lead should keep the Laravel Cloud graphs (CPU, memory, workers, database connections, queue) for each run window above, to confirm which resource ran out first.
After the test

Left to clean up

  • The buyer account used for the test holds 10 free tickets for the Load Test Event, and one sign-in token was created for it: delete them with the other test data.
  • The X-BFF-Secret and the buyer account's password were shared during the test: rotate both.
  • The shared test environment was unavailable or very slow from 09:33 to 09:48 UTC and from 09:53 to 09:58 UTC (12:33–12:58 local), and recovered by itself.

Method: k6 scenarios matching sections 5–7 of the plan (layout calls in parallel like a browser, think time 3–10 s, progress every 10 s, purchase then "my tickets" after 1, 2, 3, 5, 5 s). Every run checked that answers came from the loadtest organisation and did not follow redirects. Response times are measured at the client; network time was about 40 ms per request.

Limitations: one test machine (its CPU reached 77% during Load, still able to send the load) and one buyer account. The server-side causes come from reading the code; the Laravel Cloud settings (cache store, Octane, workers, pooler) need confirming in the environment.
